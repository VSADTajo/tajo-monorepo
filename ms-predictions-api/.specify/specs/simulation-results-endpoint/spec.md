# Feature: Simulation Results Endpoint — ms-predictions-api

**Status**: Clarified
**Created**: 2026-07-10
**Last Updated**: 2026-07-10
**Related umbrella**: cross-service work spanning ms-predictions-api → ms-gateway-api → vsad-tajo-frontend. This spec covers ONLY the ms-predictions-api piece.

---

## Overview

`ms-predictions-api` already persists predictions and their time-series results (`prediction_results`) linked to a manual simulation via `simulationId`. Today the existing `GET /simulations/manual/:id` returns simulation metadata and its maneuvers but not the produced predictions. Operators inspecting a manual simulation from the frontend cannot see the model output.

This feature adds a read-only endpoint that, given a manual `simulationId`, returns every `Prediction` linked to it together with its full time-series `PredictionResult` records, so the frontend (via the gateway) can render the outcome of a manual simulation.

---

## User Scenarios

### US1: Retrieve Results of a Finalized Manual Simulation [P1]

**As a** system operator using the frontend
**I want** to fetch the full model output of a manual simulation
**So that** I can visualize predicted time series (per station and prediction type) generated by the run

**Acceptance Criteria:**
- Given a manual simulation that reached `FINALIZED` status and has associated predictions with results
- When the results endpoint is called with the simulation ID
- Then the response contains the simulation identity (id, simulationDate, status, type), every prediction linked to the simulation with its metadata (station, prediction type, provider, percentile, prediction date window), and each prediction's ordered list of `{ date, value, flag }` time-series entries

**Edge Cases:**
- The simulation exists but is still processing (`CREATED`, `MODEL_PROCESSING`, `IN_PROGRESS`): the endpoint responds successfully, returning an empty predictions array and the current simulation status so the frontend can render a "no results yet" state.
- The simulation exists but failed (`MODEL_FAILED`): the endpoint responds successfully, empty predictions array, current status returned so the frontend can render a "failed" state.

---

### US2: Reject Non-Manual or Missing Simulations [P1]

**As a** consumer of the endpoint
**I want** clear, distinct errors when the target does not exist or is not a manual simulation
**So that** the gateway/frontend can distinguish "wrong resource" from "wrong ID"

**Acceptance Criteria:**
- Given a `simulationId` that does not exist (or is soft-deleted)
- When the results endpoint is called
- Then a 404 Not Found is returned with a clear error message

- Given a `simulationId` that exists but its `type` is not `MANUAL`
- When the results endpoint is called
- Then a 404 Not Found is returned (the endpoint scope is manual simulations only)

- Given an invalid UUID
- When the results endpoint is called
- Then a 400 Bad Request is returned

---

### US3: Deterministic Ordering for Frontend Charts [P2]

**As a** frontend chart component
**I want** results ordered predictably
**So that** rendering time-series graphs does not require client-side sorting

**Acceptance Criteria:**
- Given a simulation with multiple predictions and each prediction has multiple time-series entries
- When the endpoint returns
- Then predictions are ordered by `(stationId ASC, predictionTypeId ASC)` and time-series entries within a prediction are ordered by `date ASC`

---

### US4: Manual Curl / Script Example for QA [P2]

**As a** developer or QA
**I want** a documented example (curl and/or a small script) that exercises the endpoint
**So that** I can validate the pipeline locally without opening the frontend

**Acceptance Criteria:**
- Given the manual simulation flow has been run locally (existing example already produces a FINALIZED simulation with predictions)
- When following the documented example
- Then the caller receives the results payload and can inspect it in the terminal

## Functional Requirements

| ID | Requirement | Priority |
|----|-------------|----------|
| FR-001 | The service MUST expose a read-only endpoint that, given a manual simulation identifier, returns the simulation identity, its predictions, and each prediction's ordered time-series results in a single response. | P1 |
| FR-002 | The response MUST include, for the simulation: id, simulationDate, status, type, dataOrigin, createdAt, updatedAt. | P1 |
| FR-003 | For each prediction returned, the response MUST include: id, stationId, stationName, predictionTypeId, predictionType code/name, percentile, predictionProvider, predictedBy, predictionDate, predictionStartDate, predictionEndDate. | P1 |
| FR-004 | For each prediction's time-series result the response MUST include: date, value, flag. | P1 |
| FR-005 | The endpoint MUST return 404 when the simulation does not exist, is soft-deleted, or is not of type MANUAL. | P1 |
| FR-006 | The endpoint MUST return 400 when the provided identifier is not a valid UUID. | P1 |
| FR-007 | The endpoint MUST succeed with an empty predictions array when the manual simulation exists but has no persisted predictions yet (regardless of current status). | P1 |
| FR-008 | Predictions MUST be ordered by `(stationId ASC, predictionTypeId ASC)`; time-series entries within a prediction MUST be ordered by `date ASC`. | P2 |
| FR-009 | The endpoint MUST be discoverable in Swagger with request/response schemas and error responses documented. | P1 |
| FR-010 | Integration tests MUST exercise the endpoint through HTTP (Testcontainers PostgreSQL), including: happy path with results, empty results (no predictions yet), non-manual simulation → 404, missing simulation → 404, invalid UUID → 400. | P1 |
| FR-011 | A documented manual invocation example (curl or shell script) MUST be committed alongside the feature so operators can exercise the endpoint locally after running the existing manual simulation example. | P2 |
| FR-012 | Cache behavior: reads MAY go through the existing `CachingQueryBus`. If cached, the cache MUST be invalidated whenever new predictions are persisted for that simulation (i.e., in the existing `timeseries.ingested` consumer path). | P2 |

## Success Criteria

- [ ] Calling the endpoint with a `simulationId` of a FINALIZED manual simulation with predictions returns a payload containing the simulation, all its predictions, and all their time-series results.
- [ ] Calling the endpoint with a `simulationId` of a manual simulation with no predictions yet returns HTTP 200 with an empty `predictions` array and the current simulation status.
- [ ] Calling the endpoint with a non-existent or non-manual `simulationId` returns HTTP 404.
- [ ] Calling the endpoint with an invalid UUID returns HTTP 400.
- [ ] Integration tests cover all four scenarios above and pass under `npm run test:e2e`.
- [ ] Swagger at `/docs` documents the new endpoint including request path, response schema, and error responses.
- [ ] A committed example (`docs/examples/` or equivalent) shows how to invoke the endpoint against a locally running stack and inspect the payload.
- [ ] Response time for a simulation with ≤50 predictions and ≤2000 time-series entries per prediction is under 500 ms warm and under 2 s cold on the local dev stack.

---

## Assumptions

- The `Prediction.simulationId` and `PredictionResult.predictionId` FKs already established (existing migrations) are correct and sufficient — no schema changes required for this feature.
- Deleted simulations (`deletedAt IS NOT NULL`) are considered absent from the read model (behaves like 404).
- Response payload size is acceptable for realistic manual-simulation runs; pagination is NOT required for MVP. If real-world usage exceeds the FR-004 size targets, pagination will be added in a follow-up spec.
- The gateway (`ms-gateway-api`) will proxy this endpoint verbatim, and the frontend will consume it. Those pieces are out of scope for this spec (each service will get its own spec).
- Authorization follows the same pattern as the existing `GET /simulations/manual/:id` endpoint; no new RBAC checks are introduced.

---

## Out of Scope

- Changes to the automatic (`AUTOMATIC`) or forecast (`FORECAST`) simulation flows.
- Any changes to how predictions are persisted (that already happens via the `timeseries.ingested` consumer).
- Pagination of predictions or time-series entries.
- Aggregation/summarization of results (min/max/avg) — the endpoint returns raw entries only.
- Streaming/WebSocket delivery of incremental results.
- Gateway proxy work (`ms-gateway-api`) and frontend consumption (`vsad-tajo-frontend`) — separate specs.

## Design Decisions (resolved)

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Endpoint path: `GET /simulations/manual/:id/results` (dedicated sub-resource) | Keeps existing `GET /simulations/manual/:id` payload slim; sub-resource is idiomatic and lets the frontend fetch metadata and results independently. |
| 2 | Response does NOT include maneuvers | Maneuvers already returned by `GET /simulations/manual/:id`; duplicating them here bloats the payload and forces two update paths on schema changes. |
| 3 | Read goes through `CachingQueryBus` with explicit invalidation | Results are immutable once persisted; TTL 60 s, cache key `simulation-results:{id}`, invalidated in every code path that persists predictions for a simulation (currently the `timeseries.ingested` consumer via `ProcessTimeSeriesHandler`). |

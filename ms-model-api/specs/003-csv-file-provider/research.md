# Research: CSV File Provider

## R-001: CSV Download via ms-sftp-api

**Decision**: Download CSV files using `responseType: 'arraybuffer'` from ms-sftp-api and decode with `iconv-lite` for encoding support.

**Rationale**: The existing SFTP provider uses `responseType: 'json'` because it fetches PI-JSON files. CSV files are text with potential non-UTF-8 encoding (ISO-8859-1/Windows-1252 for Spanish characters like ALAGON, m3/s, Pluviometria). Downloading as arraybuffer allows explicit decoding.

**Alternatives considered**:
- `responseType: 'text'` — Would work if encoding is always UTF-8, but Tagus_FlowCast.csv uses ISO-8859-1
- `responseType: 'stream'` — Overkill for ~5MB files; adds complexity without meaningful benefit at this scale

## R-002: CSV Parsing Approach

**Decision**: Use a custom line-by-line parser (no external CSV library) that processes the multi-block format.

**Rationale**: The Tagus_FlowCast.csv is NOT a standard CSV (no headers row, no uniform columns). It's a proprietary multi-block format where metadata headers use tab separators and data lines use semicolons. Standard CSV libraries (csv-parser, papaparse) expect uniform row-based formats and would not handle the block structure. A custom parser is simpler and more reliable.

**Alternatives considered**:
- `papaparse` / `csv-parser` — Designed for standard CSV; would need awkward workarounds for the multi-block format
- Line-by-line streaming (`readline`) — Considered for very large files, but the current file (~5MB, 113K lines) fits comfortably in memory

## R-003: Character Encoding

**Decision**: Use `iconv-lite` to decode arraybuffer as ISO-8859-1. This is a zero-dependency pure-JS library already widely used in Node.js.

**Rationale**: The CSV contains characters like ALAGON (ALAGÓN), m3/s (m³/s), Pluviometria (Pluviometría) that are multi-byte in UTF-8 but single-byte in ISO-8859-1. The file was generated by a Windows system (FlowCast) and uses ISO-8859-1 encoding.

**Alternatives considered**:
- Node.js native `TextDecoder('iso-8859-1')` — Available in Node 22+, zero dependency. Preferred over iconv-lite.
- `iconv-lite` — Proven library but adds a dependency. Fallback if TextDecoder has issues.

**Final decision update**: Use native `TextDecoder('iso-8859-1')` since Node 22 is the minimum runtime. No new dependency needed.

## R-004: Provider Type Registration

**Decision**: Add `CSV_FILE = 'CSV_FILE'` to the `ProviderType` enum. No changes needed to `ProviderTypeValueObject` since it validates dynamically against `Object.values(ProviderType)`.

**Rationale**: Follows the existing pattern exactly. The enum addition auto-propagates to validation.

**Alternatives considered**:
- Extending SFTP_FILE with a `fileFormat` setting — Would mix JSON and CSV parsing logic in one service, violating single responsibility
- Creating a generic FILE provider — Over-engineering; SFTP_FILE already exists for JSON files, CSV_FILE is clear and specific

## R-005: Block Parsing Algorithm

**Decision**: Split file content by lines, iterate sequentially. When a line starts with "Station Site:", begin a new block. Collect 15 header lines (tab-separated key:value), then collect data lines until the next "Station Site:" or EOF.

**Rationale**: The format is strictly sequential — blocks never nest or overlap. A simple state machine (HEADER vs DATA) handles it cleanly.

**Algorithm**:
1. Split file into lines
2. Iterate lines:
   - If line starts with "Station Site:" → push previous block (if any), start new block header
   - If in header mode (lines 1-15 of block) → parse `Key:\tValue`
   - If in data mode → parse `DD/MM/YYYY;HH:MM:SS;value`
3. After loop → push final block
4. Map each block to NormalizedTimeSeriesResult

## R-006: Date Parsing

**Decision**: Parse `DD/MM/YYYY;HH:MM:SS` as European date format, convert to ISO 8601 `YYYY-MM-DDTHH:MM:SS.000Z`.

**Rationale**: The semicolon between date and time is the same separator used between all fields in data lines. Split by `;` gives `[date, time, value]`. Then reformat date from `DD/MM/YYYY` to `YYYY-MM-DD`.

**Implementation**: Simple string manipulation, no Date library needed:
```
"07/04/2026" → parts = ["07", "04", "2026"] → "2026-04-07"
combined: "2026-04-07T18:45:00.000Z"
```

## R-007: timeStep Mapping

**Decision**: Infer timeStep from parameter type:
- `Q` (Caudal) → `{ unit: 'MINUTE', multiplier: 15 }` (15-minute intervals)
- `Precip` (Precipitación) → `{ unit: 'MINUTE', multiplier: 60 }` (1-hour intervals)

**Rationale**: The time step is not explicitly stated in the CSV headers but is consistent per parameter type across all observed files. This mapping is stable and documented in the spec.

## R-008: ms-sftp-api Download for Non-JSON

**Decision**: The ms-sftp-api `/files/download` endpoint returns raw file content. The response type depends on what axios requests. Using `responseType: 'arraybuffer'` will return the raw bytes, which we decode manually.

**Rationale**: ms-sftp-api reads the file from disk and sends it back. It doesn't enforce JSON — the existing SFTP provider just happens to request JSON because it expects JSON files. For CSV, we request arraybuffer.
